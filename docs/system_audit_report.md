# CCA DocTrack – Complete System Audit Report

**Date:** November 29, 2026 (Asia/Manila)  
**Institution:** Christ Centered Academy of Lipa City, Inc.  
**Platform:** CCA DocTrack – Student Document Request Tracking System  
**Stack:** Node.js, Express.js, Supabase (PostgreSQL), Vanilla ES6+ HTML/CSS/JS, Render PaaS  

---

## 1. Executive Summary

This audit report documents all discovered defects, security vulnerabilities, business logic errors, and architectural deficiencies within the existing CCA DocTrack codebase and Supabase database. The system is being enhanced from a basic prototype into an institutional-grade, secure, multi-tier document request management platform.

## 2. Comprehensive Deficiency Matrix

| Category | Finding / Issue | Affected Components | Severity | Remediation Strategy |
|---|---|---|---|---|
| **1. Registration & Seed Logic** | Newly registered students inherit sample document requests and fallback profile data. | `db.js` (`seedDefaultRequests`), `public/script.js` (`localStorage['cca_student_profile']`, `syncStudentRefProfile`) | **CRITICAL** | Eliminate sample request insertion from production startup; decouple profile caching from generic localStorage keys; enforce clean zero-state for new students. |
| **2. Data Ownership & Relations** | `document_requests` lacks a `user_id` foreign key referencing `users.id`. Requests are linked only by loose `student_id` and `email` string matches. | `supabase_schema.sql`, `db.js` (`dbRequests.getAll`, `create`), `routes/requestRoutes.js` | **CRITICAL** | Add `user_id BIGINT REFERENCES public.users(id) ON DELETE CASCADE`. Ensure all database reads, updates, and listings enforce user ownership. |
| **3. Authentication Backdoors** | Insecure login shortcuts: allows hardcoded `'admin123'`/`'student123'` override and plaintext password comparison (`user.password === rawPassword`). | `routes/authRoutes.js` (lines 198–235) | **HIGH (Vulnerability)** | Remove all plaintext comparisons, password bypasses, and hardcoded shortcuts; enforce strict `bcrypt.compare` against database hashes. |
| **4. Date & Timezone Drift** | Application relies on client-side UTC dates (`new Date().toISOString().split('T')[0]`), causing date discrepancies around Philippine midnight (UTC+8). | `public/script.js`, `routes/requestRoutes.js`, `db.js` | **HIGH** | Establish authoritative server-side Philippine time (`Asia/Manila`) using `TIMESTAMPTZ` and dedicated separate date columns (`date_submitted`, `pickup_date`, `estimated_release_date`, `completed_at`, `created_at`, `updated_at`). |
| **5. Missing Core Tables** | System lacks tables for document settings, inventory, attachments, audit logs, notifications, and scheduling. | Supabase PostgreSQL schema | **HIGH** | Author clean, idempotent migration scripts creating `document_types`, `student_profiles`, `request_activity_logs`, `inventory_items`, `inventory_transactions`, `notifications`, `school_holidays`, and `system_settings`. |
| **6. Overwritten Historical Dates** | Status updates or profile edits could inadvertently update or overwrite historical submission timestamps. | `db.js`, `public/script.js` | **MEDIUM** | Freeze `date_submitted` once created; only modify `updated_at` and status-specific date fields. |
| **7. Lack of Quantity Controls** | No backend quantity validation or copy limits per request/day; students can request arbitrary quantities. | `routes/requestRoutes.js`, `public/script.js` | **MEDIUM** | Implement document type configuration (min/max quantity, daily limits, pending request limits) and enforce them in the backend API. |
| **8. Unchecked Inventory Deduction** | No tracking of physical stock (bond paper, special paper, envelopes, folders); no material consumption on release. | System Architecture | **MEDIUM** | Implement physical materials inventory with automated deduction upon confirmed document release. |
| **9. Insecure Public Anon Access** | Broad RLS policies allow public anonymous access to submit or query requests without ownership enforcement. | `supabase_schema.sql` | **MEDIUM** | Harden RLS policies so students only query/read requests linked to their own `user_id` or session, while admins manage all. |
| **10. Weak Pickup Verification** | Documents are marked complete without verification or proof of identity; no claim receipt or QR verification. | Request Workflow | **MEDIUM** | Implement unique pickup codes / QR verification with claimant identity capture (Self / Parent / Representative). |

## 4. Phase-by-Phase Remediation Roadmap

1. **Phase 1: Database Migration**:
   - Write and apply `supabase_migration_v2.sql` to add missing columns to `document_requests` (`user_id`, `request_number`, `quantity`, `estimated_release_date`, `completed_at`, `rejection_reason`, `pickup_code`, `claimant_name`, `claimant_relation`, `updated_at`).
   - Create tables: `document_types`, `student_profiles`, `inventory_items`, `inventory_transactions`, `notifications`, `audit_logs`, `request_activity_logs`, `school_holidays`, `system_settings`.
   - Seed default document types and initial inventory stock if empty.
2. **Phase 2: Authentication & Registration Hardening**:
   - Remove plaintext password comparison and backdoor credentials in `routes/authRoutes.js`.
   - Remove sample request seeding in `db.js`.
   - Remove cross-student fallback logic in `public/script.js`.
3. **Phase 3: Philippine Timezone & Server-Authoritative Dates**:
   - Implement server-side Asia/Manila date utilities in backend (`utils/dateUtils.js`).
   - Update frontend formatting with explicit `timeZone: 'Asia/Manila'`.
4. **Phase 4: Document Settings, Limits, Capacity & Scheduling**:
   - Add routes and database operations for document type settings and daily capacity calculation.
   - Implement backend quantity validation and overbooking checks.
5. **Phase 5: Inventory, QR Pickup Verification & Audit Logs**:
   - Add inventory management endpoints and automatic material deduction upon document release.
   - Implement pickup code generation and claiming verification workflow.
   - Implement immutable audit logging and real-time notification dispatching.
6. **Phase 6: UI & Dashboard Analytics Enhancement**:
   - Update student portal: clean 0-state, quantity selector, tracking with QR code.
   - Update administrator dashboard with real dynamic statistics, inventory alerts, and verification scanner.
7. **Phase 7: End-to-End Verification & Documentation**:
   - Run integration and HTTP regression tests, update Postman collection, update README.
